# Spec 872 — A 1581 drive

**Status:** MERGED 2026-09-23 (main, after v0.8.8) — as built in §11
**Repos:** TRX64. C64RE: no change in this spec. Its media tools keep mounting D64/G64
on drive 8 until a separate request asks for D81.
**Number:** 872 (registry: `../../../C64ReverseEngineeringMCP/specs/README.md`).
**Depends on:** Spec 870 (the drive as a part: power, own reset, stopped, ROM latched at
power-on, unit 8-11, accessors, `drivePart` node) and Spec 871 (positions A/B, one bus
with two devices, `Device::Drive(unit)`, unit numbers on the wire). A 1581 is a second
kind of board in a position that already exists. It is not a third drive.
**Enables:** D81 media. It is also the second of the two drive types the U64 FPGA
builds, after the 1541 (`c1581_drive.vhd`).
**Origin:** the owner, 2026-09-23. The U64 can switch each drive position between
1541, 1571 and 1581 (`software/drive/c1541.cc:24`, `set_drive_type` `:906-943`). UE2 plays
position A with TRX64's drive, so a 1581 selected there has nothing to run on.

**Sources read end to end:**
- **VICE**, the port source: `drive/iec/cia1581d.c`, `drive/iec/wd1770.c`,
  `drive/iec/fdd.c`, `drive/iec/memiec.c`, `drive/iec/iec.c`, `iecbus/iecbus.c`
  (conf1-3), `drive/drivesync.c`, `drive/drivecpu.c`, `drive/drive-snapshot.c`,
  `drive/driverom.[ch]`, `diskimage/fsimage-probe.c`, `diskimage/fsimage-dxx.c`,
  `c64/c64fastiec.c`, `c64/c64cia1.c`, `c64/c64cia2.c` and `core/ciacore.c` (SDR, FLAG,
  snapshot).
- **Ultimate**: `software/drive/c1581.cc/h` (the older sector-level class),
  `wd177x.cc/h` + `mfmdisk.cc/h` (the current one, driven from `c1541.cc`), `mm_drive.h`.
  The software alone says nothing about pins or timing, so the FPGA side was read too:
  `fpga/1541/vhdl_source/cpu_part_1581.vhd`, `c1581_drive.vhd`, `wd177x.vhd`.
- **Hardware, the authority** (2026-09-23, zimmers.net): the 1581 Service Manual
  PN-314982-01 with schematic #252380 rev. 4 and its parts list, the WD1770/1772 data
  sheet, the CSG 8520 data sheet, and a disassembly of `dos1581-318045-02.bin`. They

- **TRX64**: `drive.rs`, `iec.rs`, `cia.rs`, `drive_6510core.rs`, `drive_snapshot.rs`,
  `lib.rs` (the drive positions and the ROM boot), and the daemon's media paths.

## §1 What exists today (v0.8.8)

- **One kind of board.** Both positions hold a `Drive1541` (`lib.rs:546`, `:551`). Its
  bus is hard-wired to the 1541 map: 2 KiB RAM, VIA1, VIA2, the GCR rotation
  (`drive.rs:394-470`). `DiskKind` is `D64 | G64` (`drive.rs:31-35`). The daemon maps
  every format string to one of those two (`trx64-daemon/src/main.rs:8912`, `:9213`,
  `:9647`, `:9814`).
- **The IEC core already knows a 1581.** `DriveType::Drive1581` exists
  (`iec.rs:56-57`). The conf1/2/3 write paths return `AtnEdge::Cia1581Flag { fire }` on
  an ATN edge (`iec.rs:228-230`, `:626-630`), a port of `iecbus.c:250-252`, `:313-315` and
  `:383-385`: the 1581 takes ATN on its CIA's FLAG pin, not on a VIA CA1. The core also
  has the 1581's ATN-acknowledge term, which is an OR where the 1541 has an XOR
  (`iec.rs:600-616` = `iecbus.c:271-276`). Nothing sets `unit_type` to it yet, and
  `iec_drive_write` still folds with the 1541 formula only (`iec.rs:400-407`).
- **The drive CPU core is reusable.** `DriveCore6510` is generic over
  `DriveCore6510Bus` (`drive_6510core.rs:315-337`). The only 1541-specific hooks are
  `rotate`, `byte_ready` and `byte_ready_edge_clear`. VICE calls the same hooks on a
  1581, and there `rotation_rotate_disk` returns at once because no VIA2 has switched
  `BRA_MOTOR_ON` (`rotation.c:1106-1111`). A 1581 bus answers them with nothing.
- **The CIA core is not yet a drive CIA.** `cia.rs` is the C64's two CIAs. It has
  timers, ICR and TOD, but no FLAG input, no serial shift register (a write to `$xC`
  only stores the byte: `cia.rs:913-916`) and no port hooks. `irq_asserted` is a
  latched-level test (`cia.rs:932-934`), not VICE's ciacore IFR/alarm pipeline. The
  1581's whole ATN handling runs on a FLAG interrupt (`iecbus.c:250-252`), so the CIA has
  to grow before a 1581 can answer the bus.
- **ROMs.** `boot_from_dir` gives both positions the 1541 DOS
  (`lib.rs:2923-2950`, `drive.rs:642-646`). No 1581 ROM is looked for.

## §2 D1 — The board

A 1581 is a new part type, `Drive1581`, beside `Drive1541`. It has its own 6502 and is
never merged into the C64 core, which is the same rule the 1541 lives under. Its map,
ported from `memiec.c:249-255`:

| range | device | VICE | Ultimate FPGA |
|---|---|---|---|
| `$0000-$1FFF` | 8 KiB RAM | `drive_ram`, page 0 via the zero functions | ext. memory (`cpu_part_1581.vhd:171`) |
| `$2000-$3FFF` | nothing decoded (74LS139 U6 Y1 unconnected, sheet 1) | unmapped: `drive_read_free` returns `cpu_last_data` (`drivemem.c:75-78`) | reads `$FF` (`:216-222`) |
| `$4000-$5FFF` | 8520 CIA, 16-byte mirror | `cia1581_read/store` | `cia_registers`, `addr(3..0)` |
| `$6000-$7FFF` | WD177x, 4-byte mirror | `wd1770d_*`, `addr & 3` (`wd1770.c:998-1012`) | `wd177x`, `addr(1..0)` |
| `$8000-$FFFF` | 32 KiB ROM | `drive_read_rom`, no store | ROM, writes ignored (`:174-180`) |

- **Clock: 2 MHz.** VICE's `clock_frequency` is 2 for a 1581 (`drivesync.c:98-103`), and
  the sync factor is `clock_frequency × floor(65536·10⁶ / cpu_hz)` (`drivesync.c:47-60`).
  With Spec 863 that gives 133 034 on PAL and 128 158 on NTSC. The U64 runs its 1581
  with `two_MHz_mode => '1'` (`c1581_drive.vhd:150`).
- **CPU: NMOS 6502**, `drivecpu`, not the 65C02 core, which VICE keeps for 2000/4000/CMDHD
  only (`drive-snapshot.c:288-296`). The U64 uses `cpu6502(cycle_exact)`. IRQ is the CIA
  alone and NMI is not connected (`cia1581d.c:271`, `cpu_part_1581.vhd:150`). Neither
  source wires the WD177x's INTRQ or DRQ to the CPU. The DOS polls the status register.
- **RAM power-on pattern:** zeros, the 870 decision (VICE `lib_calloc`). The DRIVECPU
  module carries `0x2000` bytes for a 1581 (`drivecpu.c:616-621`, `:709-714`).
- **Open bus at `$2000-$3FFF`** follows VICE (`cpu_last_data`). The board confirms it
  (§10.4): U6 (74LS139, schematic #252380 sheet 1) decodes A13/A14 with A15 as its
  enable. Y0 goes to the RAM, Y2 is `/6526SEL`, Y3 is `/WDSEL`, and **Y1 (pin 5) is not
  connected**. The ROM's `/OE` is `NAND(R/W, A15)` (U7), and the data bus has no
  pull-ups. Nothing drives the bus in that range. Ultimate's `$FF` has no basis on the
  board.
- **Address decode is by A13-A15 only.** The CIA (RS0-RS3 = A0-A3) and the WD (A0-A1)
  repeat through their 8 KiB windows, which is where the mirrors in the table above come
  from. The ROM is
  selected by A15 on reads only, and a write to `$8000-$FFFF` selects nothing.

### D1a — CIA port bits (the glue)

The 1581 has no separate glue chip: the CIA's ports are the glue. Every bit below is
taken from the code on both sides.

| bit | port A (`$4000`) | port B (`$4001`) |
|---|---|---|
| 0 | out: **side select**. VICE `side = PA0 ? 0 : 1` (`cia1581d.c:136`) | in: DATA, inverted (`^0x85`, `:215-217`) |
| 1 | in: **/RDY**, straight from the mechanism (CN2 pin 34, 1 kΩ pull-up RP1-2/R15; sheets 2-3). VICE reads 0, always ready (`:194-201`); U64 `not(motor and inserted)` (`c1581_drive.vhd:217`) | out: DATA out |
| 2 | out: **/MOTOR**. VICE `motor = PA2 ? 0 : 1` (`:137`) | in: CLK, inverted |
| 3-4 | in: **device jumpers**, `8 × number` (`:194`). U64 `drive_address` (`cpu_part_1581.vhd:301`) | 3 out: CLK out · 4 out: ATN acknowledge |
| 5 | out: power LED (U64 `:300`; VICE ignores it) | out: **fast-serial direction** → `iec_fast_drive_direction` (`:181`) |
| 6 | out: **activity LED** (`:139`) | in: **/WPS**, 1 = writable (`read_only ? 0 : 0x40`, `:217`) |
| 7 | in: **/DISK CHANGE**, 0 = changed (`:196-198`) | in: ATN, inverted |

- **ATN** arrives twice: as PB7 (level) and as a FLAG edge on the falling ATN
  (`iecbus.c:250-252`; U64 `flag_i => atn_i`, `cpu_part_1581.vhd:268`).
- **A port-B store** folds the drive's lines into the bus with the 1581 formula
  (`cia1581d.c:153-183`). That is the OR form of the ATN acknowledge, not the 1541's XOR,
  and it is the same term the IEC core already carries (`iec.rs:604-610`).
  `iec_drive_write` gets a type-aware sibling. The 1541 path does not change.
- **Unit number, 8-11.** The 870 rules hold unchanged: the jumpers are latched at the
  drive's reset and the bus slot follows them. Only the mechanism differs. On the 1581 the
  jumpers are CIA PA3/PA4, where on the 1541 they are VIA1 PB5/PB6.
- **CIA serial port (SP/CNT) = fast serial.** On a 1581, SP is the DATA line and CNT is
  SRQ, switched by PB5 through a 74LS241 (U64 `cpu_part_1581.vhd:278-284`). The schematic
  confirms it (sheet 3, U13 74LS241 + U11 7407). PB5 drives both enables, `OE2` (pin 19)
  and `/OE1` (pin 1). **PB5 = 1:** SP → 2A4 → 2Y4 → 7407 → bus DATA, and CNT → 2A1 →
  2Y1 → 7407 → FAST CLK (SRQ, CN4 pin 1). Both are open-collector and non-inverting.
  **PB5 = 0:** bus DATA → 1A3 → 1Y3 → SP, and SRQ → 1A4 → 1Y4 → CNT. The 2Y outputs
  float, and 1 kΩ pull-ups (RP1-12, RP1-15) keep the 7407s released. The DOS holds PB5
  high in its fast send paths (`$ACD4-$ACDB`, `$ADAD-$ADB8`). They are gated by `$76`
  bit 5, and that bit is set in one place only: the IRQ handler (`$DAFD-$DB10`), when the
  ICR shows SP (a byte arrived in the SDR) and `$76` bit 3 is set. The byte has to be
  clocked in on CNT, that is SRQ. **Corrected at build:** `$DBCF` is not gated. It sits in
  `$DBC7`, which `$ACBB` calls at the end of every ATN sequence (`$AEE4`, `$AEEC`) to reset
  the shift register by toggling CRA's SP mode. It raises PB5 for exactly 32 cycles, from
  `STA $4001` at `$DBCF` to `STA $4001` at `$ACCA`, with no byte in the SDR. The build
  measured those pulses, 32 cycles each (§11). Reset leaves PB5 = 0 (`$AF30`: PRB `$D5`). VICE models
  this at byte level only: a drive SDR store goes to the C64's CIA1 or CIA2 SDR, and only
  when the "burst mod" is configured (`c64fastiec.c:100-117`; default
  `BURST_MOD_NONE`). **A stock C64 has no path for it.** Its SRQ is wired to CIA1 FLAG
  (cassette), and CIA1/CIA2 SP/CNT go to the user port. Fast serial is therefore modelled
  on the drive side only, with no C64 side (§8).

### D1b — The CIA grows what the 1581 needs

`cia.rs` gains the following, ported from `core/ciacore.c`:
- the **FLAG** input (`ciacore_set_flag`, `ciacore.c:1621-1625`: an async interrupt with
  `CIA_IM_FLG`);
- the **serial data register** in both directions, with VICE's `sdr_delay` machinery
  (`ciacore.c:59-99`, `:690-735`, `:915-932`, `:1495-1505`) and `ciacore_set_sdr` /
  `ciacore_set_cnt` (`:1631-1670`);
- **port A/B read/store hooks** (VICE `read_ciapa`, `store_ciapa`, …);
- the **IRQ line** as ciacore drives it (`cia_set_int_clk` → `interrupt_set_irq`,
  `cia1581d.c:75-83`).

The C64's two CIAs do not wire any of these: FLAG stays unconnected, SP/CNT stay open,
and the hooks are no-ops. **They must stay byte-identical**, which the 7-game gate and
`cia_alarm_check_gate` guard (§9).

**The TOD is an 8520 event counter, and the 1581 uses it to tell which WD is fitted.**
VICE runs the drive CIA as a 6526: `cia1581d.c` sets no model, so the calloc'd context
is `CIA_MODEL_6526`, with a BCD clock ticked at `1 000 000 / 50` (`cia1581d.c:266`,
`:295-302`). The real part is an 8520A-1 (U5). Its TOD is a **24-bit binary counter that
counts positive edges on the TOD pin**, with no 50/60 Hz prescaler. Registers `$8/$9/$A`
are event bits 0-7/8-15/16-23 and `$B` is not connected. A write stops the counter until
the LSB is written. A read of the MSB latches all three until the LSB is read. CRB7
selects the alarm (8520 data sheet §1.5.10 and the register map; service manual
p. 8). On the board (sheet 3) the TOD pin (19) has a 2.7 kΩ pull-up (R5) and goes
through jumper J1 to PHI2. The note on the sheet reads "J1 installed for WD1770 (U4).
Removed for WD1772 (U4)", and the parts list has U4 = WD1772 (C310651-02), the WD1770
as a substitute, and "J1 (Use only with WD1770)". The DOS reads it exactly once, at
reset (`$C36A-$C385`): `STA $4008` #0, then 84 cycles through `JSR $AD2F`, then
`LDA $4008`. **Zero** means no edges, so a WD1772: it INCs the five type-I command bytes
at `$01DA-$01DE`, setting r1r0 from 00 to 01. **Nonzero** means a WD1770, and the DOS
keeps 00. No other code in the ROM touches `$4008-$400B`, and the ICR mask (`$9A`,
`$AF49`) leaves the alarm interrupt off. **Ported as the standard board: WD1772 with
J1 open.** The TOD pin is static high, the counter never moves, and the DOS takes the
1772 branch. The 8520 TOD registers are ported as the binary counter above, not
ciacore's BCD clock. The U64 does the same by tying the pin to `'1'`
(`cpu_part_1581.vhd:241`). VICE's 50 Hz BCD tick is not ported. It takes the same
branch only because a tenth rarely rolls over within the 84 cycles.

## §3 D2 — The WD177x

A new `wd177x.rs`, a 1:1 port of `wd1770.c` (with the `fdd.c` mechanism under it, §4).
It runs lazily against the drive clock, as VICE's does. `wd1770_execute` catches up on
every register read or write (`wd1770.c:825`, `:891`).

**Registers** (`addr & 3`): 0 status/command, 1 track, 2 sector, 3 data
(`wd1770.c:68-74`). A status read clears the IRQ flag. A data read or write clears DRQ
(`:882-885`, `:894-903`). The peek has no side effects (`:909-922`).

**Commands** (`wd1770.c:109-140`, mask and type table): type I RESTORE `0x`,
SEEK `1x`, STEP `2x/3x`, STEP-IN `4x/5x`, STEP-OUT `6x/7x`; type II READ SECTOR `8x/9x`,
WRITE SECTOR `Ax/Bx`; type III READ ADDRESS `Cx`, READ TRACK `Ex`, WRITE TRACK `Fx`;
type IV FORCE INTERRUPT `Dx`. The flag bits are h (spin-up disable), V (verify), r1r0
(step rate), u (update track register), m (multiple), E (settle delay) and a0 (deleted
data mark).

**Status** (`wd1770.c:93-106`): MO, WP, SU/RT, SE/RNF, CRC, T0/LD, IP/DRQ, BSY. Type I
bits (IP, T0, WP) are refreshed only when idle after a type I command (`type == -1`,
`:210-214`).

**Timing the drive CPU can observe.** These are VICE's constants in drive cycles at
2 MHz, and they are what the port reproduces:

| what | VICE | drive cycles |
|---|---|---|
| byte time (250 kbit/s MFM) | `BYTE_RATE = f × 8000/250` (`:61`) | **64** (32 µs) |
| command accept → BUSY | `PREPARE = f × 24` (`:63`, `:233-237`) | 48 (= the data sheet's 24 µs MFM bound, §10.2) |
| step rate r1r0 = 0..3 | `wd1770_step_rate[is1772]` (`:54-57`, `:62`) | 12 000 / 24 000 / 4 000 / 6 000, the **1772** table (`is1772 = 1`, the fitted part, §10.1). The DOS uses r1r0 = 01 only: 24 000 (12 ms) |
| head settle (V or E) | `SETTLING = f × 30000` (`:60`) | 60 000 (30 ms). The 1772 data sheet gives 15 ms for E. The DOS never sets V or E (§10.1), so nothing reaches it |
| spin-up (h = 0, motor off) | 6 index pulses (`:249-256`) | ≈ 2.4 M |
| motor-off when idle | ≥ 10 index pulses (`:222-224`) | ≈ 4 M |
| verify gives up (SE) | 6 index pulses (`:328-332`) | |
| type II gives up (RNF) | 5 index pulses (`:426-430`) | |
| READ ADDRESS gives up | 6 index pulses (`:675-679`) | |
| lost data on write | no DRQ served 9 bytes after it was raised (`:541-545`) | |
| revolution | `raw.size = 25 × 250` bytes (`fdd.c:211`) | 400 000 (200 ms, 300 rpm) |
| index pulse | `INDEXLEN` = 16 bytes (`fdd.c:56`, `:583`) | 1 024 |

The read path raises DRQ on each byte and sets LD if the previous byte was not taken,
and it goes on reading (`:515`). READ ADDRESS writes the ID's track byte into the sector
register (`:702-704`). RESTORE runs as SEEK to 0 from `track = 0xFF`. At track 0 it sends
no step pulse (`:269-272`, `:292-296`), so a RESTORE on track 0 leaves the disk-change
latch set. That is what the hardware does, and §10 notes Ultimate's difference.

**Reset** (`wd1770_reset`, `:931-941`): registers 0, `step = -1`, `clk` = now. The FDD
(head position, motor, disk) is **not** reset. The head is mechanical, which matches
870's "the disk is a medium, not state of the electronics".

## §4 D3 — The MFM disk and the D81

**The surface** is VICE's `fdd.c` model, ported 1:1. The unit is a byte, not a flux bit.
One track is 6 250 bytes, each carrying a sync flag, so `0x1A1` means A1 with the missing
clock (`fdd.c:237-255`, `:626-652`). Only the one track under the head is resident
(`raw.track_head = track·2 + head`). It is built from the image on demand
(`fdd_update_raw`, `:435-557`) and decoded back into sectors when it is dirty and the head
leaves it (`fdd_flush_raw`, `:265-433`).

**Resident track layout (D81, ISO):** 32 × `4E` (gap 4a, no index mark), then per sector
12 × `00`, 3 × `A1`*, `FE`, track, side, sector, `02`, CRC-hi, CRC-lo, 22 × `4E`,
12 × `00`, 3 × `A1`*, `FB`, 512 data, CRC-hi, CRC-lo, 35 × `4E`. Ten sectors, and the rest
of the 6 250 bytes is `4E` (`fdd.c:459-544`, gaps `:202-208`). The CRC is CCITT with
preset `B230` for the ID and `E295` for data (`fdd.c:117-135`, `:483`, `:495`).

**Geometry.** Physical: 80 tracks (0-79) × 2 sides × 10 sectors (1-10) × 512 bytes. The
head moves up to track 83 (`FDD_MAX_TRACK`, `fdd.c:52`; U64 `cur_track /= 83`,
`c1581_drive.vhd:225`). Logical, as the DOS and the image see it: 80 tracks (1-80) ×
40 sectors (0-39) × 256 bytes. Logical track = physical track + 1. Logical sectors 0-19
are side 0, 20-39 side 1, two per physical sector (`fdd.c:392-396`, `:454-457`).

**Sides are inverted, and that is the hardware.** `head_invert = 1` (`fdd.c:104`,
`:203`). The ID field's side byte and the image order use `head ^ 1`. Physical head 1 (PA0
low) therefore carries logical side 0. That is why a PC reads a 1581 disk with its heads
swapped. Ultimate's `MfmDisk` stores the logical side in the table and in file order
(`mfmdisk.cc:110-134`) and leaves the physical mapping to the FPGA's `side_0` pin. Both
agree on the D81 byte order.

**D81 image.** It is 819 200 bytes (3 200 × 256). VICE also accepts 81, 82 and 83
tracks, each with or without the error-info block (`diskimage.h:39-46`,
`fsimage-probe.c:255-310`). **All eight sizes are accepted.** `DiskKind` gains `D81`.
The error-info bytes are kept and written back unchanged, but **they do not shape the
surface**. VICE's `fdd_update_raw` checks only `res < 0` (`fdd.c:517-520`). A hard error
from `disk_image_read_sector` is a positive code that leaves the buffer untouched
(`fsimage-dxx.c:365-400`), so VICE builds that sector from the previous sector's bytes
under a valid CRC. That is a defect and is not ported: a sector is always built from its
own bytes, as the Ultimate does (`mfmdisk.cc:110-133`, `c1541.cc:583`). Decided by the owner
(§10.6): kept and ignored.

**Write-back is lazy, as with the 1541.** A dirty resident track is decoded into the
image bytes in memory when the head leaves it (a track or side change), and on detach,
reset, power-off and a `disk_as_written` capture. `fdd_flush_raw` (`fdd.c:265-433`)
recovers only ID/data pairs that are well formed. A track written in a foreign layout
(WRITE TRACK with other sector sizes) keeps what the D81 can hold, and that is a
property of the format. **No read-only mount.** Persist and auto-persist write the whole
D81 back to its original file, per position, exactly as 871 does for D64/G64
(`DiskAutoPersist`). `read_only` becomes the medium's write-protect (/WPS = PB6, WD
status WP) and nothing else.

**Disk change** (`fdd.c:219`, `:234`, `:699-701`) is set on attach and detach and
cleared by a step pulse with a disk present. It reads on PA7, active low.
**Motor and index:** without a disk or with the motor off, the surface does not turn and
no index pulse comes (`fdd_rotate`, `fdd.c:563-565`). The head steps only while the
motor is on (`fdd.c:696-698`), which is VICE's rule.

## §5 D4 — How it plugs into 870/871

- **A position holds a board of one type**: `Drive1541` or `Drive1581`, behind one enum.
  `Machine::drive8` and `drive_b` hold the enum. The `pair_*` functions (`drive.rs:1642-1715`)
  dispatch per type: catch-up, fold into IEC with the type's formula, and deliver ATN
  (VIA1 CA1 for a 1541, CIA FLAG for a 1581). The IEC core's `unit_type[slot]` is set from
  the position's type whenever the slot map is rebuilt (`sync_drive_slots` /
  `adopt_drive_slots`).
- **The part state is shared.** `DrivePart` (`drive.rs:1578-1618`) is power, held,
  stopped, reset-line connection, unit and jumpers, and it means the same thing for a 1581.
  870's gate at the top of `run_cycles` (off / held / stopped runs no cycle) and its bus
  rules (off or held puts nothing on the bus and yields Conf0 when nothing is left) apply
  unchanged. A 1581 held in reset drives nothing, including the ATN-acknowledge term.
- **The type is chosen at power-on.** `Machine::set_drive_type(pos, T)` is refused while
  the position is powered, and the refusal names the position and says to switch it off
  first. Off, the new type is built fresh: RAM zero and its own ROM (below). The mounted
  medium must fit the type. A D81 in a 1541 position or a D64/G64 in a 1581 position is
  refused, naming the type. The medium is kept only if it fits. Otherwise it is ejected,
  after the write-back. There is no automatic type switch on mount. Ultimate offers one
  (`c1541.cc:1019-1022`), but the type is the owner's choice, not a guess from a file.
- **The ROM is latched at power-on and only then.** This is the owner's rule and 870 §4.
  A 1581 takes **exactly 32 KiB** at `$8000-$FFFF`. VICE loads with min = max = `0x8000`
  (`iecrom.c:125-128`, `driverom.h:46`). Any other size is refused, naming the size and
  the type. 870's 16 KiB form stays a 1541 thing. Ultimate mirrors a 16 KiB file for any
  type (`c1541.cc:937-939`), and that is not taken over. A ROM given to a powered 1581
  waits for its next power-on. A reset keeps the ROM it has.
- **Reset, held, stopped and the reset line** behave as in 870 §3/§3a. A 1581 reset is
  `ciacore_reset` + `wd1770_reset` (`iec.c:108-111`), write-back first, and the disk is
  kept.
- **Two positions and the unit rule** are 871's. Two powered drives at one unit are
  refused whatever their types. **A 1541 at 8 and a 1581 at 9** is a legal and tested
  machine (§9).
- **Defaults do not move.** Both positions are 1541s, A on at 8 and B off. A machine that
  never asks for a 1581 is byte-for-byte today's machine.

## §6 D5 — Checkpoints

Checkpoints use the `.c64re` container with the VICE module layout, the convention
`drive_snapshot.rs` already follows. The 1541 blob uses VICE names for unit 0 inside each
position's blob (`DRIVE8` / `DRIVECPU0`, `drive_snapshot.rs:253`, `:470`). A 1581 blob is
the same, in VICE's order for `DRIVE_TYPE_1581` (`drive-snapshot.c:162-354`,
`iec.c:271-280`):

| module | version | carries |
|---|---|---|
| `DRIVE8` | 2.0 (`drive-snapshot.c:159-160`) | `type` = 1581, `clock_frequency` = 2, GCR/rotation fields as VICE writes them for a non-GCR drive |
| `DRIVECPU0` | TRX64's 1.4 (DRIVECPU doc) | registers, **`0x2000` RAM** (`drivecpu.c:616-621`), interrupt status |
| `CIA1581D0` | 2.5 (`ciacore.c:2141-2142`, name `cia1581d.c:272`) | the full ciacore state incl. SDR and IFR |
| `WD1770<n>` | 1.0 (`wd1770.c:1014-1079`) | registers, command/type/step, `byte_count`, `tmp`, `direction`, `clk`, `irq`, `dden`, `sync`, `is1772` |
| `FDD<4n>` | 1.0 (`fdd.c:753-823`; the name is `FDD` + `4 × mynumber`, `wd1770.c:183`) | head, motor, side, disk change, write protect, geometry, `index_count`, `raw.head`, the **resident track** `raw.data` + `raw.sync` and `raw.dirty` |

- **The disk rides as written**, the rule 871 closed with `fix-drive-int-snapshot`. The
  image carried is the D81 a persist would write at the capture instant. It is built on a
  copy by the write-back's own decoder, with the dirty resident track folded in and in
  the mounted size (80-83 tracks, error block kept). On restore the whole D81 is mounted,
  then the FDD module puts the resident track back byte for byte. A persist after the
  restore writes the whole disk. The layout in the container is VICE's `IMAGE<n>` 1.0
  (type word `1581`, then the sectors, `drive-snapshot.c:656-721`). VICE has no
  "as-written" rule and the `FDD` module says `TODO: Disk image save` (`fdd.c:821`), so
  this part is TRX64's.
- **Not ported from VICE:** `SMW_DW(m, (uint8_t)drv->raw.head)` truncates the head
  position to 8 bits (`fdd.c:812`). TRX64 writes the full value. A VICE reader reads a
  DWORD and gets it right, but a VICE-written module restores with a wrong head. The
  version check in `wd1770_snapshot_read_module` compares the minor against
  `WD1770_SNAP_MAJOR` (`wd1770.c:1093`). The check is ported with the minor where it
  belongs.
- **`drivePart` gains `board_type`** (serde default `1541`). A checkpoint written before
  872 restores both positions as 1541s, as it always did. A position whose type changes
  on restore gets its power-on for the ROM, the path 871 built for B (`latch_rom`).
- **Round trip is cycle-exact**, the same bar as 871 §9.1.7: the restored machine runs
  in lockstep with the straight run.
- The drive ROM is not in the checkpoint. That is 870's open item, and it applies here
  unchanged.

## §7 D6 — API and daemon

- **Core.** `Machine::set_drive_type(pos, DriveType)`, refused while powered.
  `Drive1581::set_rom(&[u8])` accepts 32 KiB only. Accessors, read-only and free of side
  effects as in 870 §6: `ram()` (8 KiB), `ports()` → CIA PA/PB as the pins see them (side,
  /RDY, motor, jumpers, LEDs, disk change, IEC in/out, fast-serial direction, /WPS),
  `wd()` → track, sector, data, status, command, busy and the step phase, and
  `head() → (track, side)`.
- **ROM supply.** Commodore IP is not bundled: ROMs stay gitignored and local, as
  `README.md:33` and `.gitignore` (`docker/roms/`) have it. `boot_from_dir` also looks for
  `dos1581-318045-02.bin` (VICE's name, `driverom.h:96`), then the aliases `1581.bin`
  and `1581.rom` (Ultimate's default config name, `c1581.cc:27`). This is non-fatal, as
  for the 1541. The copies on this machine at `vice/data/DRIVES/` and
  `1541ultimate/roms/1581.bin` are the same image, SHA-1 `01228eae…d393`, 32 768 bytes.
  A 1581 with no ROM runs a zero ROM, the 870 behaviour.
- **Wire** (unit numbers on the wire and positions inside, 871 §8):
  - `session/drive_type {unit, type: "1541"|"1581"}` is new. It is refused while powered,
    naming the position.
  - `media/ingress|mount|swap|unmount|persist` accept `d81`, detected by extension and one
    of the eight sizes. A medium that does not fit the drive at that unit is refused,
    naming its type.
  - `session/state` `drives[]` gains `type`. `session/read_memory` with
    `space: "drive<unit>"` reads the 1581 map.
  - The monitor: `device drive<unit>` works on a 1581 (its map, its CIA/WD in the I/O
    view), and `drive [unit]` shows the type.
- **Not extended to a 1581:** the head trace (Spec 784, a GCR thing), the `iec` verb's
  drive column, the `.vsf` export (871 already records it as A/1541-only). The
  `drive8-cpu` trace domain follows position A's CPU whatever its type.

## §9 Acceptance

**Gate: must pass.** Every test runs over the real KERNAL and the real 1581 DOS from the
local ROM directory.

1. **Directory.** A 1581 at 8 with a D81: `LOAD"$",8` lists the image's directory,
   header, ID and blocks free exactly as a static D81 read of the same file gives them.
2. **KERNAL LOAD.** `LOAD"FILE",8,1` puts a PRG into memory byte-identical to the PRG in
   the image. The PRG spans a track boundary and both sides.
3. **KERNAL SAVE.** `SAVE"NEW",8` and then a persist leave a D81 whose `NEW` is
   byte-identical to the saved RAM range. BAM and directory are consistent (a static
   check), and every other sector is unchanged. The same image mounted in a fresh machine
   loads `NEW` back.
4. **Format.** `OPEN15,8,15,"N:TEST,72"` on a blank-filled D81 writes all 160 physical
   tracks through WRITE TRACK and leaves a D81 that a static reader accepts: header at
   40/0, BAM at 40/1-2, 3 160 blocks free. That image mounted again lists `TEST`.
5. **A 1541 and a 1581 on one bus.** A 1541 at 8 (A) and a 1581 at 9 (B). A plain BASIC
   loop, as in 871 test 4, copies a SEQ with every byte value 8 → 9 and 9 → 8. Both arrive
   byte-identical after persist, and each source image is unchanged.
6. **Disk change.** A D81 swapped while the 1581 is powered: the next `LOAD"$",8` lists
   the new disk. With no disk, `LOAD"$",8` fails in the drive with job code `$03`, and the
   error channel then reads `74,DRIVE NOT READY` (§10.3). What the C64 prints for the
   failed LOAD is recorded by name.
7. **870 rules on a 1581.** Off gives DEVICE NOT PRESENT. Off → on runs a power-on with
   the D81 kept. Held and stopped behave as 870 §8.3/§8.8. The reset line connected versus
   cut works. A 32 KiB ROM from bytes boots, and 16 KiB and other sizes are refused,
   naming the size and the type. A ROM given while powered waits for the power-on.
   `set_drive_type` while powered is refused, naming the position.
8. **Checkpoint round trip.** Captures mid-LOAD, and mid-SAVE with a dirty resident track,
   go through a `.c64re` container into a freshly booted machine. The restored state
   (C64 RAM, drive RAM, CIA, WD, FDD, clocks, bus map) equals the captured one. The
   restored run stays in cycle-for-cycle lockstep with the straight run for 500 frames.
   The persisted D81 afterwards is identical to the straight run's. A checkpoint from
   before 872 restores with both positions as 1541s.
9. **WD timing as the drive sees it.** Unit tests on `wd177x.rs` check each row of the
   §3 table in drive cycles against the port's constants: BUSY after a command write,
   STEP/SEEK per track at each rate, the settle delay, the spin-up to the first DRQ, the
   byte period of consecutive DRQs, RNF after the index count, and lost data on a write.
   One live test measures the same thing from the drive CPU through the CIA timer (a
   SEEK issued by `M-E` code). There is no VICE oracle: the constants are ported and
   tested for what they say.
10. **Fast serial is not observable from a stock C64, and the gate says so.** During
    tests 1-5 the 1581's PB5 (fast-serial direction) is recorded at every change. The DOS
    sends over SP only after a byte has arrived in the SDR over SRQ (§D1a, §10.7), and a
    stock C64 never clocks SRQ. **Corrected at build:** PB5 does go to 1, for the 32-cycle
    `$DBC7` pulse at the end of every ATN sequence (§D1a), so "PB5 must stay 0" was wrong
    against the ROM. The test now fails if PB5 is ever high for longer than that pulse,
    if it is left high, or if the serial port shifts a byte out. A burst send would hold
    PB5 for a whole byte and count one. Nothing more about burst is testable on a C64.
11. **Nothing else moved.** With defaults (A = 1541 at 8, B off) the 7-game gate is 7/7
    with all seven screenshots byte-identical to 871's. `cia_alarm_check_gate`,
    `drive_part_gate`, `second_drive_gate` and every drive gate are unchanged.
    `cargo test -p trx64-core` and `-p trx64-daemon` pass.

**Characterisation: recorded, not a pass/fail gate.**

12. **The 7 games with a 1581 idle at 9.** Each game is judged by its picture against the
    B-off frame of the same build, as 871 §9.1.1 does. A 1581 also answers every ATN, in
    its acknowledge term and its DOS. The three ATN-signalling loaders that differed with
    a 1541 at 9 (Green Beret, MOTM, Scramble) are expected to differ here too. Any
    difference is recorded with its first divergence.
13. **Cost.** Frame time with B off, a 1541 idle at 9, and a 1581 idle at 9, on the same
    workload. The 1581 runs twice the drive cycles.

## §10 Open questions for the owner

Default where not stated: VICE, as ported.

Primary sources for items 1-5 and 7, all read on 2026-09-23: the 1581 Service Manual
PN-314982-01 (June 1987) with schematic #252380 rev. 4, sheets 1-4, and its parts list;
the WD1770/1772 data sheet scans; the CSG 8520 data sheet (all from zimmers.net); and a
disassembly of `dos1581-318045-02.bin`, where every address below is a ROM address.
VICE and Ultimate were used only as the things being checked.

1. **WD1770 or WD1772 step table. SETTLED 2026-09-23.** The DOS issues exactly one set
   of WD commands. They are built at reset into RAM `$01DA-$01E4` (`$C30C-$C340`):
   RESTORE `$08`, SEEK `$18`, STEP `$28`, STEP-IN `$48`, STEP-OUT `$68`, READ `$88`,
   WRITE `$AA`, READ ADDRESS `$C8`, READ TRACK `$E8`, WRITE TRACK `$FA`, FORCE INT `$D0`.
   All go through `$CBF4` (`STA $6000`), or `$CFD1` for `$D0`. Nothing else writes
   those bytes except the P bit of `$01E0`/`$01E3` (`$CFEA-$D009`). In every type-I
   byte r1r0 = 00, and V = E = 0 throughout. The TOD probe at `$C36A-$C385` (§D1b) INCs
   the five type-I bytes to r1r0 = **01** when the TOD does not count, which is a WD1772
   board. **The DOS uses only 00 and 01, and those are 6 ms and 12 ms on both chips**
   (WD177x data sheet, the stepping-rate table, scan p. 6). The fitted part is the
   **WD1772** (parts list: U4 = C310651-02, "U4 Sub." = WD1770; sheet 3 note on J1).
   Decision: `is1772 = 1`, J1 open. The DOS then steps at 12 ms (r1r0 = 01), which is the
   rate VICE and the U64 already get, because neither TOD counts. The 1772 values for
   10/11 (2/3 ms) and its 15 ms E delay can be reached only by user code (`M-W`/`M-E`).
   Confidence: high.
2. **BUSY after a command write. SETTLED 2026-09-23.** The data sheet (programmed-I/O
   delay table, scan p. 16) specifies "Write to Command Reg. → Read Busy Bit (Status
   Bit 0): 48 µs FM / **24 µs MFM**", then 32 µs for status bits 1-7 and 16 µs to read
   back the same register. The 1581 runs MFM: `/DDEN` (pin 26) is tied to GND (sheet 2).
   The data sheet guarantees BUSY only once 24 µs have passed, which is **48 cycles at
   2 MHz**. Before that the bit is unspecified. VICE's `PREPARE` = 48 is exactly that
   bound. The U64's "at once" is also legal, but it is the earliest possible case, not
   evidence. The ROM reads inside the window. `$CBF4`: `STA $6000`, `LDA #$01`,
   `BIT $6000`, `BEQ` back. The first read comes 6 cycles after the write, and the loop
   **waits for BUSY to go high**. Then `JMP $AD34` delays, and later `$CBEC` waits for
   BUSY to go low. After FORCE INT the DOS waits 3 × `$AD2F` before it polls (`$CFD4-$CFE0`).
   Either timing therefore ends up in the same state. The only difference is how many
   times the `$CBFA` loop runs (≈7 cycles each). Decision: **keep 48** (the data sheet
   bound). Confidence: high on the data sheet and the ROM. The real chip's exact latency
   inside 0-24 µs is not given anywhere.
3. **/RDY. SETTLED 2026-09-23 for the board and the DOS; the mechanism's timing stays
   open.** Board (sheets 2-3): /RDY is CN2 pin 34 from the Chinon mechanism, with a 1 kΩ
   pull-up (RP1-2/R15), wired straight to CIA PA1 (pin 3) with no gating by the board.
   /DISK CHNG is CN2 pin 2, with a pull-up (R2), to PA7 (pin 9). /MOTOR (PA2) and SIDE0
   (PA0) go out through 7407 U11 to CN2 pins 16 and 32. DOS: `$CDBC` samples PA1 30
   times (`LDY #$1E`), and every sample must read 0, otherwise it returns carry set.
   `$CD83-$CDA8`: when PA7 = 0 (changed), it issues STEP-IN + STEP-OUT (`$01DD`,
   `$01DE`), waits, and reads PA7 again. Still 0 gives job code `$03`. Both failures
   give job code `$03` (`$CDA8`, `$CD39`). The job-error handler (`$A7AE`, reached
   through `$FF2D` → vector `$01AE`, set from the table at `$FF75`) maps codes `$03`,
   `$0E` and `$0F` to **DOS error `$74` = 74, DRIVE NOT READY** (`$A7C1-$A7CD`; the
   message is at `$A6F3`). **LOAD with no disk: 74, DRIVE NOT READY.** VICE's
   always-ready gives the same result by the disk-change path: `fdd.c` starts with
   `disk_change = 1` (`:105`) and clears it only on a step with a disk in (`:700`). So
   test 6 does not depend on the /RDY model. Still open: when the Chinon F-354E asserts
   READY relative to motor-on and insertion, i.e. whether the U64's
   `not(motor and inserted)` without a delay is right. Missing source: the Chinon
   F-354E/FB-354 drive specification (not on zimmers.net). Until it turns up, the default
   stays VICE, as the header of this section says. It is not observable through the
   stock DOS with no disk (see above).
4. **`$2000-$3FFF`. SETTLED 2026-09-23: open bus.** Sheet 1: 74LS139 U6 (first half)
   has `G` = A15, `A` = A13, `B` = A14. Y0 (pin 4) drives RAM U3 `/CS1`+`/OE`, Y2
   (pin 6) is `/6526SEL`, Y3 (pin 7) is `/WDSEL`, and **Y1 (pin 5) is unconnected**. ROM
   U2: `/CS` is tied to GND and `/OE` = `NAND(R/W, A15)` (U7 74LS00). Sheet 1 has no
   pull-up on D0-D7. The 4 × 2.7 kΩ RP2 goes to the CPU's control inputs. Nothing drives D0-D7 for `$2000-$3FFF`, so the CPU reads a floating bus. VICE's
   `cpu_last_data` is the port. The U64's `$FF` is not what the board does. Confidence:
   high that nothing is decoded. The floating value is electrical, and no document gives
   it. "Last byte on the bus" is the model.
5. **The drive CIA's TOD. SETTLED 2026-09-23.** The 8520 TOD is a 24-bit **binary**
   event counter clocked by positive edges on the TOD pin, not a BCD clock (8520 data
   sheet §1.5.10; the service manual register map calls `$8-$A` "Event LSB/8-15/MSB"
   and `$B` "No Connect"). The pin goes to PHI2 through J1 only on WD1770 boards.
   Otherwise it is held high by R5 (sheet 3). The DOS reads it once, as a chip probe
   (`$C36A-$C375`), and nowhere else. Details and the decision (8520 counter, pin
   static) are in §D1b. Confidence: high.
6. **D81 error bytes. DECIDED 2026-09-23 (owner): kept and ignored, as the Ultimate.** The
   Ultimate never reads them: it takes the track count as file size / 10240
   (`c1541.cc:583`) and maps each sector straight to its file offset
   (`mfmdisk.cc:110-133`), so every sector reads clean with its own bytes. VICE also
   ignores them, but builds a flagged sector from the previous sector's bytes under a valid
   CRC (`fdd.c:517-520`, `fsimage-dxx.c:365-400`); that is not ported (§4).
7. **SP onto DATA. SETTLED 2026-09-23.** Yes. With PB5 = 1, SP drives bus DATA and CNT
   drives SRQ, both through 74LS241 U13 and open-collector 7407 U11. With PB5 = 0 the
   direction is reversed (bus → SP/CNT). Pin level is in §D1a. The DOS sends with PB5 = 1
   only after the CIA has shifted in a byte on CNT/SRQ (IRQ `$DAFD-$DB10` → `$76` bit 5 →
   `$ADAD-$ADB8`, `$ACD4-$ACDB`), and a stock C64 never clocks SRQ. (Corrected at build:
   `$DBC7` also raises PB5, for 32 cycles, at the end of every ATN sequence; §D1a.) VICE's byte-level
   model is enough for scope §8, and test 10 guards the assumption. Confidence: high.
8. **Type change while powered.** Decided as "refused, switch off first" (§5).
   Alternative: pending until power-on, as the ROM is. That is simpler for a host, but it
   leaves a window in which the mounted medium and the type in force disagree.

## §11 As built (2026-09-23, branch `spec-872-1581`)

**Where it lives.** `ciacore.rs` (the drive CIA), `wd177x.rs` + `fdd.rs` (controller and
mechanism), `drive1581.rs` (the board), wired into `drive.rs`, `iec.rs`, `full.rs`,
`drive_snapshot.rs`, `c64re_snapshot.rs`, the daemon, the monitor and the session.

- **The position, not an enum (deviation from §5's wording).** `Machine::drive8` and
  `drive_b` keep their type, `Drive1541`: since 870 that struct is the position. It holds
  the part state (power, reset, stopped, reset line, unit, jumpers) and the medium record,
  and for a 1581 `board_1581: Option<Box<Drive1581>>`. The 1541 electronics stay in the
  struct, neither clocked nor on the bus then. The dispatch §5 asks for sits where it
  would sit behind an enum: `run_cycles`, the IEC output, ATN delivery, reset, power, ROM,
  the medium and the accessors. The 428 `drive8.*` call sites keep compiling and keep
  meaning the 1541 where they read 1541 internals. `board_type()`, `board_1581()` and
  `cpu()` answer per board.
- **The CIA beside `cia.rs`, not inside it (deviation from §D1b's wording).**
  `ciacore.rs` is `core/ciacore.c` ported 1:1: IFR and SDR delay lines, FLAG, SDR/CNT/SP,
  port hooks, the IRQ line, snapshot 2.5. It shares only the timer (`cia::Ciat` and its
  transition table) with the C64's CIAs, so those stay byte-identical by construction.
  Model 6526, as VICE (`cia1581d.c` sets none). `cia_set_int_clk` events are replayed
  into the drive CPU's `IntStatus` in order at the instruction boundary. The RMW re-store
  is the CPU core's dummy store (TRX64's drive core never sets `rmw_flag`). The 8520 TOD
  is §D1b's counter. `$B` reads 0: it is not connected, and no document gives a value.
- **IEC.** `iec_drive_write_typed` folds a 1581 with the OR formula. `set_slot_type` and
  `pair_slot_types` keep `unit_type` in step with the positions at every sync point, and
  `pair_deliver_atn_edge` hands the 1581 its FLAG edge. **Found and fixed:** conf3 read
  `unit_type[dnr]` (slots 0-3) where VICE's `diskunit_context[dnr]->type` is the unit at
  slot `dnr + 8`. Every slot was a 1541, so nothing had moved.

**Decided at build, not stated:**
1. **BUSY latency.** VICE counts PREPARE from the controller's own clock, which idles on
   the 64-cycle byte grid. BUSY therefore rises 0 to 48 cycles after the command write,
   and exactly 48 when the write falls on a byte boundary. §3's "48" is that bound. The
   unit test checks both.
2. **No disk, motor on.** VICE would build the resident track into a NULL buffer. Here
   the surface is a blank track with no sync, and the WD runs into its index count.
3. **A 1581 reset keeps the mechanism and the medium mounted.** It writes back first,
   then runs `ciacore_reset` + `wd1770_reset` + the CPU reset. There is no re-attach, so
   the disk-change latch stays as it was.
4. **The DOS's track cache.** The 1581 DOS writes its cached track back on its own
   schedule, after `READY.`. A host that persists then persists what the drive has not
   written yet, as a user who ejects with the LED lit would. The gates wait for the motor
   to stop. Auto-persist is unaffected, because it runs on the write report.
5. **Checkpoints.** The capture settles the CIA module before it writes DRIVECPU0, so the
   interrupt status includes what the settle raised. The modules sit in VICE's order.
   `IMAGE0` carries the D81 as written, error block included: a TRX64 extension after
   VICE's sectors, bounded by the module's size. `prepare_drive_types(m, cp)` sets the
   board types before a host re-attaches media (a D81 fits only a 1581), and
   `restore_runtime_checkpoint` runs it too. The board's own IEC output is re-derived from
   CIA PB on restore, because VICE's `undump_ciapb` for the 1581 is empty. `boardType` is
   written only for a 1581, which is why `cia_alarm_check_gate` did not move.
6. **Daemon.** A D81 is recognised by size. None of the eight sizes can be a D64, a G64
   or a PRG. A `.d81` name on any other length is refused. `session/drive_type` takes
   `"1541"`/`"1581"` or the number. A medium that does not fit the new type is persisted
   to its host file before it is ejected, and the reply names it. A C64 power cycle keeps
